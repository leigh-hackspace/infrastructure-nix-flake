## 0. TL;DR — the mission plan

1. Your camera is a **SigmaStar SSC333 (Infinity6B0)**, 64 MB RAM, 8 MB SPI NOR, SSW‑101B USB

## 3. Flash layout (two independent sources agree)

The kernel builds MTDs from a **RedBoot FIS table** at boot (boot log), and the TP‑Link image
manifest at 0x80000 carries the same map — cross-checked, identical. ✅

| MTD  | Name           | Offset   | Size             | Contents (verified)                                                                                                                                                                                                                                                                                                                                                                                                      |
| ---- | -------------- | -------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| mtd0 | `factory_boot` | 0x000000 | 0x2D800 (182K)   | IPL (`IPL_`, ARM, `IPL g77fc04e`) + backup IPL + `MXP` partition-info at 0xF000 (`MXPT` entries: IPL@0, IPL_CUST@0x7000, MXP@0xF000, UBOOT@0x10000)                                                                                                                                                                                                                                                                      |
| mtd1 | `factory_info` | 0x02D800 | 0x2800 (10K)     | factory data (mostly erased/0xFF here)                                                                                                                                                                                                                                                                                                                                                                                   |
| mtd2 | `art`          | 0x030000 | 0x10000 (64K)    | header `"C110_2.0"` + **16-byte high-entropy field @ +0x46** (per-device key candidate) + gzip tar of calibration/config                                                                                                                                                                                                                                                                                                 |
| mtd3 | `config`       | 0x040000 | 0x20000 (128K)   | **encrypted key-value store** (magic `FF FF FF FF AB 01 CD 23 01 AB`), the app's settings live here (§7)                                                                                                                                                                                                                                                                                                                 |
| mtd4 | `normal_boot`  | 0x060000 | 0x20000 (128K)   | second-stage **U‑Boot 2015.01** `jenkins-tapo_c110v2_develop-218`, XZ-compressed uImage `MVX4##I6B0g3932d50CM_UBT1501#XVM`                                                                                                                                                                                                                                                                                               |
| mtd5 | `kernel`       | 0x080000 | 0x168200 (1440K) | 512‑B TP manifest + uImage **Linux‑4.9.84**, load/entry `0x20008000`, data 1,473,112 B, u‑boot treats as "uncompressed" (ARM zImage self-decompresses internal XZ)                                                                                                                                                                                                                                                       |
| mtd6 | `rootfs`       | 0x1E8200 | 0x257E00 (2399K) | **squashfs 2,372,334 B, XZ**, mounted read-only as `/` (`root=/dev/mtdblock6`)                                                                                                                                                                                                                                                                                                                                           |
| mtd7 | `rootfs_data`  | 0x440000 | 0x3BFE00 (3839K) | **the application/system squashfs** (3,686,290 B, XZ) — despite the OpenWrt-ish name it is NOT a jffs2 overlay; `spdev=/dev/mtdblock7` is mounted at `/sp_rom` by `lib/preinit/70_pivot_jffs2_root` and merged into `/` via overlayfs (`lib/functions/boot.sh:133`, `lowerdir=/sp_rom:/`). Runtime root = mtd6 ∪ mtd7. The last 344 KiB (0x7D0000–0x7FFE00) is erased 0xFF (jffs2 space when the overlay is initialised) |
| mtd8 | `verify`       | 0x7FFE00 | 0x200 (512B)     | signed manifest: `00000100 55AA9DD1…` + 9-entry (offset,size) table + 64 B signature blob + `"C110 2.0"` + 16 random bytes + counter `01`                                                                                                                                                                                                                                                                                |
| mtd9 | `firmware`     | 0x080000 | 0x780000         | overlay view (kernel+rootfs+rootfs_data) for upgrades                                                                                                                                                                                                                                                                                                                                                                    |

Notes:

- First/last partitions don't sit on erase boundaries → kernel force-read-only's several of them. ✅
- Despite the name, `rootfs_data` here holds no jffs2 user data on this unit — user settings are in
  the encrypted `config` partition instead. (OpenWrt-style `mount_root` would create jffs2 there if
  absent; TP‑Link's flow clearly doesn't.) ⚙️ inference from mount flow.
- The `verify` manifest is checked by neither IPL nor u‑boot `bootcmd` (§5). It is used by the
  upgrade/recovery tooling (`/sbin/slpupgrade`, `/sbin/slprestore`, `recover-manager` init script).

## 4. Boot chain (verified from your UART log + the binaries)

```
BROM (SoC internal)
 └─ IPL @0x0               "IPL g77fc04e", SPI 54M, 64MB DRAM, BIST
     └─ MXP @0xF000        → IPL_CUST @0x7000 (XZ, board init)
         └─ UBOOT @0x10000 first-stage U-Boot 2015.01 (XZ, "Version: I6ga7e5767")
             │  prints "Autobooting in 1 seconds", runs "Uip boot..." (tiny IP stack),
             │  prints "Firmware check pass!"  ← no actual verification ✅
             └─ sf read 0x20008000 0x60000 0x20000 → XZ-decompress to 0x220A0000 → jump
                 └─ second-stage U-Boot 2015.01 (XZ, "Version: I6g3932d50")
                     bootcmd = sf probe 0; sf read 0x20008000 0x80000 0x300000; bootm 0x20008200
                     bootargs= console=ttyS0,115200n8r root=/dev/mtdblock6 rootfstype=squashfs
                               spdev=/dev/mtdblock7 noinitrd init=/etc/preinit
                               LX_MEM=0x3FE0000 mma_heap=mma_heap_name0,miu=0,sz=0x1220000 ...
                     └─ Linux 4.9.84 (zImage self-decompress) → squashfs root + /etc/preinit
```

What's **not** here: verified boot. No efuse signing in play (IPL _supports_ `Authenticate image
failed!`/CUST-key paths but this SKU doesn't fuse it — it prints `Checksum OK` and proceeds),
u‑boot does CRC-only `Verifying Checksum` on the uImage, and its `sigauth`/`AESON`/`AESOFF`
commands exist but are **not invoked by `bootcmd`**. Consequence: any kernel/rootfs image with a
valid uImage CRC boots — which is precisely how OpenIPC is installed. ✅

Second-stage u‑boot extras found in binary (`carve/uboot-ssc333.bin`): `slp` (SigmaStar loader
shell), `sfbin`, `tftpboot`/`dhcp`/`bootp`, `env`/`printenv`, `mw`/`md`, `bootdelaykey` (GPIO-gated
interrupt; default `bootdelay=0`), `riu_r`/`riu_w`, `btime`, httpd-ish `Uip` bits. ✅

## 6. What's encrypted, what's not

| Data                                               | State                                    | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Kernel / both rootfses / u‑boot on chip            | **not encrypted**                        | XZ/LZMA only; extracted ✅                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Downloadable OTA packages                          | encrypted+signed (verify-only on device) | `…_up_boot-signed_…bin` format: header `00000100 55AA…`, RSA-PSS sig, payload AES-128-CBC; AES key derived from the RSA‑PSS **salt** during signature verification against TP‑Link's embedded public key. Community tool: `watchfulip/tp-link-decrypt` (fork `robbins/tp-link-decrypt`). ⚠️ well-documented, not needed here since chip contents are plain                                                                                                                                    |
| `config` partition (app settings incl. WiFi creds) | **encrypted at rest**                    | container = `FF FF FF FF AB 01 CD 23 01 AB` + size + AES payload; same format as `/etc/sys_conf_data` (5312 B). Handler: `/usr/lib/libuc_convert.so` → `libaes.so` (`AES_cbc_Encrypt/Decrypt`); no key string recoverable statically from rootfs — a 16-byte per-device high-entropy field at `art+0x46` is the likely key material source. Family context: **CVE‑2023‑27126** — C200 v3 used a _shared_ AES key/IV for exactly this, leaking WiFi password with physical access. ⚠️/✅ mixed |
| Runtime                                            | decrypted in RAM                         | with `init=/bin/sh` boot you can just `uci show` / read `/tmp` state (§8)                                                                                                                                                                                                                                                                                                                                                                                                                     |
| TLS/kl_app nonsense                                | —                                        | see §10 myth-busting                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

**Bottom line for this project: nothing you need is actually locked.**

## 7. Optional: root shell on _stock_ firmware (no reflash)

Skip if you're going straight to OpenIPC. Useful to (a) recover your current WiFi creds in
plaintext, (b) capture the config-partition key, (c) keep stock + rooted.

1. Wire UART: 3.3 V logic, **115200 8N1**, TX/RX pads on main PCB near TP501 (your boot log came
   from here). ✅
2. Power on, hammer **Enter** during `Autobooting in 1 seconds` (first stage) — if that fails,
   let it reach the second-stage U‑Boot prompt (it also honors `bootdelaykey` GPIO; community
   reports Enter during the 1 s window works on C110 v2 ⚠️).
3. Boot the stock kernel with a shell as init (no writes needed):

   ```
   setenv bootargs "console=ttyS0,115200n8r root=/dev/mtdblock6 rootfstype=squashfs \
     spdev=/dev/mtdblock7 noinitrd init=/bin/sh LX_MEM=0x3FE0000 \
     mma_heap=mma_heap_name0,miu=0,sz=0x1220000 mma_memblock_remove=1"
   sf probe 0 ; sf read 0x20008000 0x80000 0x300000 ; bootm 0x20008200
   ```

4. You are `# root` in a minimal ash. Now:
   - `mount -t proc proc /proc; mount -t sysfs sys /sys` for tools.
   - WiFi creds: start storage/config daemons by hand or simply boot normally and use the
     `tp_manage`/`uci` stack — in `init=/bin/sh` the quickest win is running
     `/sbin/mount_root` then `/bin/tp_manage` briefly and dumping `uci show`, or
     `grep -r psk /tmp` after normal services run. ❓ (flow verified only partially)
   - Make it stick (stock-rooted option): remount overlay? Stock has no writable overlay —
     instead patch the rootfs squashfs and rewrite mtd6 (repack `mksquashfs -comp xz -b 131072`,
     `sf erase/write` from u‑boot, keep ≤0x257E00 bytes) to add `/etc/inittab` autologin or dropbear.
   - Or boot with `single`/`rescue` and replace `login` with a no-password busybox getty.
5. Serial login without step 2/3: `askfirst` prompts for `/bin/login`; password is the
   per-build root hash above (offline crack ⚠️ unknown at time of writing).

### 8.1 Prerequisites

- UART adapter (the one from your dump/boot-log setup) — **required for first install**.
- Either of:
  - **CH341A programmer + SOP8/SOIC clip** (do the 3.3 V VCC mod — pin 7 to 3.3 V, diode mod etc.), used with `flashrom` and **`snander`** (https://github.com/OpenIPC/snander-mstar, micro version https://github.com/OpenIPC/microsnander), wired **TX=SDA, RX=SCL** for snander's bit-bang mode; or
  - `flashrom -p ch341a-driver` directly (clip on the NOR while desoldered/power off).
- FAT32 micro‑SD card (≤32 GB) for image staging (optional but easiest).
- `screen`/`picocom` at 115200.

### 8.2 Step 1 — replace the boot region with OpenIPC U‑Boot (one time)

Your own gist records the proven flow (verified working on this exact board):

```bash
# chip programmed in-circuit; snander bit-bangs the UART lines (TX=SDA, RX=SCL on the CH341A)
sudo ./snander -i                 # interrupt boot within first ms → chip waits in prog mode
sudo ./snander -e                 # erase (boot region)
sudo ./snander -w u-boot-ssc333-nor.bin   # OpenIPC u-boot-sigmastar build, ~1 min
```

`u-boot-ssc333-nor.bin`: from https://github.com/OpenIPC/u-boot-sigmastar (build `ssc333 nor`,
or grab the first bytes of the full image's boot section), or from the Leigh Hackspace build
linked in your gist. Alternative without snander: `flashrom -p ch341a-driver -w` the **entire**
OpenIPC 8 MB image directly — works but leaves no stock IPL at all (the image's own IPL is fine;
this is what the full-image step does anyway) ⚠️ early attempts at partial writes bricked one board,
so flash the FULL image if you write directly.

### 8.3 Step 2 — flash the full OpenIPC image from U‑Boot (SD card)

Power up, open serial console, get the OpenIPC U‑Boot prompt (now interactive):

```
mw.b 0x21000000 0xff 0x800000
fatload mmc 0:1 0x21000000 openipc-ssc333-lite-8mb.bin     # or your filename
sf probe 0 ; sf lock 0
sf erase 0x0 0x800000
sf write 0x21000000 0x0 0x800000
reset
```

Equivalent in your gist: `fatload mmc 0 0x21000000 tapo-c110-ssc333-8mb.bin` + same
`sf erase/write` (that image came from
`https://jenkins.int.leighhack.org/job/OpenIPC-Builds/job/Tapo-C110/17/artifact/tapo-c110-ssc333-8mb.bin`
⚠️ older artifact; prefer current nightly tgz above).

TFTP alternative (no SD): `setenv ipaddr …; setenv serverip …; tftpboot 0x21000000 image.bin;
sf erase/write …`.

First boot after this: **serial login `root` / `12345`**. ✅ (change with `passwd`)

### 8.4 WiFi without the app — pick any of three ✅

1. **SD-file bootstrap (easiest first contact):** put two text files (no extension, content = raw
   value) on a FAT SD card: `wlanssid` and `wlanpass`. Power-cycle the camera. The customizer
   writes them into the boot environment, connects, and the settings persist when the card is
   removed. (Your gist documents this exact flow.)
2. **U‑Boot env vars (most reliable, scriptable for fleets):**
   ```sh
   fw_setenv wlandev ssw101b-ssc333-tapo-c110     # ← required; atbm6012b-ssc333-tapo-c110 on v2.6 boards
   fw_setenv wlanssid 'YourSSID'
   fw_setenv wlanpass 'YourPass'
   reboot
   ```
   Profile names verified live in OpenIPC firmware: `general/overlay/etc/wireless/usb`.
   Docs: https://github.com/OpenIPC/wiki (wireless-settings) — env-driven `wland`, works before
   any network exists.
3. **QR provisioning:** OpenIPC `quirc-openipc` scanner reads an OpenIPC QR
   (`wlanssid=…\nwlanpass=…`, generator: https://openipc.org/tools/qr-code-generator) or a phone's
   Wi‑Fi-share QR; camera answers with IR‑cut click codes.

Fallback addressing: no DHCP + no env creds → camera answers on **192.168.2.10** (wired `eth0`
fallback, `netaddr_fallback`) — plug in Ethernet (the SoC EMAC is live; RJ45 may need pins
soldered on v2 boards ⚠️).

### 8.5 What you get afterwards (all local, no cloud, no app)

- **Web UI** at `http://<cam-ip>/` (majestic SeaChange) — image, night mode, OSD, motion.
- **RTSP**: `rtsp://<cam-ip>:8554/mem=2/stream1` (h264; customizer pins: IR‑cut GPIO78, IR LED
  GPIO14 auto night switch ✅).
- **ONVIF** supported by majestic (`media2/profiles/tokens` etc.) → works with BlueIris, Frigate,
  Home Assistant, go2rtc, NVRs.
- **SD-card recording** with motion events (thingino-style `recordmgr` is thingino-only; OpenIPC
  Lite has its own `srecord`/majestic motion recording). ⚠️ check build config
- SSH + serial root, `fw_printenv`/`fw_setenv` for config, package-free read-only rootfs +
  overlay (`/overlay` writable).
- **Upgrades without any cloud:**
  `fw upgrade https://github.com/OpenIPC/builder/releases/download/nightly/ssc333_lite_tp-link-tapo-c110-v2-nor.tgz`

Privacy defaults after install: nothing phones home (no TP‑Link cloud binaries exist in OpenIPC

## 9. Restoring stock ("flash back") — the undo button

Keep `c110-1.bin` (sha256 above) forever. To undo OpenIPC:

```bash
# clip on NOR, camera OFF/unpowered
flashrom -p ch341a-driver -r verify1.bin        # sanity read first (expect current OpenIPC contents)
flashrom -p ch341a-driver -w c110-1.bin -v      # write + verify whole chip
```

Power-cycle → stock C110 v2 returns **exactly as dumped**, including `art` (WiFi calibration,
`SSW101B_TXPWR`), encrypted `config` (the camera's stored WiFi creds + TP‑Link binding state will
be whatever they were at dump time — if the dump predates your app pairing, you re-pair once; if
after, it rejoins your network by itself), MAC and cloud enrollment. That's the beauty of a full
chip image. ⚠️ restore fidelity assumes the dump is clean — see §11 before trusting it.

Partial restore (stock boot chain back while keeping OpenIPC boot): unnecessary; full-chip
restore is the supported path both ways (OpenIPC reflash is always one `sf write` away).

## 9A. Configuring the camera WITHOUT the app and WITHOUT reflashing (stock firmware)

**Short answer: yes, fully possible — the camera itself hosts a complete provisioning
HTTPS API in setup mode, and we extracted every piece of it from this very dump.**

### How provisioning actually works on this firmware (all ✅ from `carve/`)

The flash carries **two merged userspaces** (overlayfs at boot, §3):

- `rootfs` (mtd6, squashfs base): cloud/p2p core (`cloud-iot`, `cloud-service`, `dsd`, `tp_manage`),
  `wlan-manager`, and the `onboarding` helper (`/usr/bin/onboarding`, `/bin/onboarding.sh`).
- `rootfs_data` (mtd7, the app/system 'sp_rom', merged into `/` at runtime): patched **uhttpd** carrying the onboarding web API
  (`do_onboarding`, **`scanApList`, `connectAp`, `getConnectStatus`**, `get_rsa_pub_key/
get_rsa_pri_key`, `ubus call onboarding getWiFiList/getWiFiStatus`), the **`ffs`** daemon
  (first-setup + cloud bind via "DSS", ECDH `EVP_PKEY_derive`, `cloud_public_key`), plus
  `nvid` (ONVIF), `rtspd`, `storage_manager`, telemetry, SigmaStar factory tools under `/config`,
  and a **`telnet`** service — `etc/init.d/cet` starts `telnetd` whenever
  `/data/core_dump_debug` exists (debug backdoor path, ⚠️ untested).

The credential pipeline (all local, no cloud required):

```
[setup mode]  ffs / reset-button hotplug (etc/hotplug.d/button/10-reset)
    → ubus call onboarding switchAPMode            (or onboarding.sh ap)
    → open softAP, camera at 192.168.191.1 (AP_ADDR in etc/init.d/wlan), udhcpd hands out 192.168.191.x
    → patched uhttpd POST /  {"method":"scanApList"|"connectAp"|"getConnectStatus", "params":{"onboarding":{...}}}
    → ubus  wlan_manager.wlan_sta_connect {ssid,bssid,auth,encryption,password(base64)}
    → uci set wlan.sta0.*; uci commit wlan        → encrypted into `config` mtd (§6)
```

`/bin/onboarding.sh` on the running system is literally the appless config CLI:
`/bin/onboarding.sh sta <SSID> <PASS>` (WPA2 auth=4), `wpa3` (auth=5), `wep`, `ap` (force softAP).
The QR channel (camera optically scans a QR shown by the phone) exists in the same binary
(`qrcode` handler) but its payload format has never been published — the HTTP path does
everything, so it's not needed.

**Why this is open to us (verified):**

- Camera TLS = firmware-embedded cert+key (`etc/tp_manage/priv-key.pem`, modulus shared across
  all units; server-cert matches — same flaw class as CVE‑2025‑1099 / evilsocket's C200 finding)
  → plain `curl -k` works.
- `dsd` embeds **seven RSA-1024 private keys** in its own `.text` (fleet-wide).
- Onboarding API is **pre-auth in setup mode** on this generation: documented for C100
  (pytapo#24, same software family) and reproduced on C220/C236/D205/C113/C110-line as
  "unauthenticated `scanApList`/`connectAp`, direct (not multipleRequest-wrapped)"
  (kennedn/tapo-onboarding PR #5). Password field = RSA‑1024 PKCS#1v1.5, base64, with this
  public key (from the Tapo APK, verified live from the repo ✅):
  ```
  MIGfMA0GCSqGSIb3DQEBAQUAA4GNADCBiQKBgQC4D6i0oD/Ga5qb//RfSe8MrPVI
  rMIGecCxkcGWGj9kxxk74qQNq8XUuXoy2PczQ30BpiRHrlkbtBEPeWLpq85tfubT
  UjhBz1NPNvWrC88uaYVGvzNpgzZOqDC35961uPTuvdUa8vztcUQjEZy16WbmetRj
  URFIiWJgFCmemyYVbQIDAQAB
  ```
- Newer builds (~2024+, "encrypt_type 3") require a prior `login` (device password; default
  `TPL075526460603`) and then encrypt the same way with the per-reset `public_key` returned by
  scanApList; even newer (2025-12+ on some models, CVE‑2025‑14300 patches) close pre-auth
  `connectAp`. **Our 1.3.7 b230823 predates the closures.** ⚠️ version-dependent — test yours.
- Cloud binding (`bindToCloud`/DSS/`cloudiot`) is part of the _app's_ flow but is **optional**:
  C100/C220 run RTSP/ONVIF fully cloudless after a scripted onboard (pytapo#24: jp-0,
  JayFoxRox; kennedn skips bindToCloud).

### Bench recipe (no app, no reflash)

1. Get the camera into setup mode: hold **reset ~10 s** (factory reset; if bound, it waits ≤5 s
   for a cloud unbind — `resetWaitUnbind.sh` — then `slprestore -rf`) until the LED alternates
   green/red and an open AP `Tapo_C110_XXXX` appears. A camera that is powered up and _unbound_
   enters this mode automatically (FFS).
2. Join that AP (or reach the camera's LAN IP — pre-auth `connectAp` often answers on the
   bound/normal-mode LAN API at this generation; try both).
3. ```bash
   tools/tapo_wifi_set.sh 192.168.191.1 'MySSID' 'MyPass'
   ```
   (script in this repo; deps bash/curl/openssl/python3; RSA-encrypts the password, falls back
   to `pwd_encrypted:0` plaintext, prints `getConnectStatus` until associated.)
4. If you get auth errors ⇒ your build wants `login`: use
   `kennedn/tapo-onboarding`'s `tapo_onboard.sh 192.168.191.1 <newpass>` (handles v3 login with
   `TPL075526460603`, logo-off, third account, connectAp — all cloudless).
5. Want RTSP/ONVIF accounts without the app: same tool (`changeThirdAccount` → user `tapoadmin`,
   `setAccountEnabled`). Note: soft 5‑s reset does NOT clear the admin password.
6. From serial instead of network: boot as in §7 and run
   `/bin/onboarding.sh sta MySSID MyPass`, or call
   `ubus call wlan_manager wlan_sta_connect '{"ssid":"<b64>","bssid":"AA:BB:CC:DD:EE:FF","auth":4,"encryption":3,"password":"<b64>"}'`
   - `uci commit wlan`.

**Caveats:** firmware-dependent (§10 advisories show TP-Link closing pre-auth connectAp on newer
builds — do NOT let this camera auto-update if you want this to keep working); a factory reset on
a _bound_ camera goes through cloud unbind first (needs internet once); and everything stays
100 % reversible — §9 restores the original chip image, app pairing included.

## 9B. Can we push our **own firmware** over WiFi, with stock firmware running?

**Short answer: over WiFi, yes — we can reach a firmware-upgrade endpoint and it will run
`/sbin/slpupgrade`. But stock `slpupgrade` verifies an RSA-PSS signature with a TP-Link public key
that is embedded in the binary, so it rejects any image we sign ourselves.** The upgrade endpoint
is real; the **signature check is the wall**, not the transport.

### What the stock upgrade surface actually is (all ✅ from `carve/`)

Three entry points feed one program, `/sbin/slpupgrade`:

1. **Cloud/OTA** (`auto_upgrade` cron at ~03:xx; `cloud_upgrade`/`get_new_fwinfo` →
   `cloudiot check_fw_version` → download → `slpupgrade`). Server-side, not ours.
2. **The `/admin/system/image_upgrade` multipart upload handler** (in the `rootfs_data`
   `uhttpd`, the same server that serves `connectAp`). Verbatim from the strings:
   ```
   /sbin/slpupgrade -c %s >/dev/null 2>&1 ; echo $? > /tmp/.sysupgrade_result   # check first
   ...
   fw forbid; sleep 1; /sbin/slpupgrade %s ;                                    # then flash
   ```
   upload → check → flash, driven by the web API (`do_login`/`check_token`/`/stok=` gate the
   `/admin/...` URLs; `fac_image_upgrade` is the factory variant, `upload_conf`/`download_conf`
   the config backup/restore). **A genuine "upload firmware over the network" path exists.**
3. **SD-card file drop** — `etc/init.d/check_upgrade` (START=13): if a FAT SD card holds
   `factory_up_boot.bin`, it runs `slpupgrade -n "/tmp/sdcard/factory_up_boot.bin"` **before the
   network comes up** — no app, no login, no network.

`slpupgrade` options: `-c` check-only, `-n` no-reboot, `-h`. It parses the TP-Link update header
(hwId, OemID, vendor_id, zone_code, language) and then calls
`rsaVerifyPSSSignByBase64EncodePublicKeyBlob` → `"RSA signiture check OK"` /
`"RSA signiture check failed"`. The public key is a base64 CryptoAPI `RSA1` PUBLICKEYBLOB
(`BgIAAAw…`, 1024-bit) **inside `slpupgrade` itself** (extracted from
`carve/squashfs-root/sbin/slpupgrade`); only TP-Link holds the matching private key. We can
_decrypt_ their packages (per-image AES key is recoverable, §6 — `watchfulip/tp-link-decrypt`) but
cannot _sign_ our own. Every stock flash path therefore stops at `RSA signiture check failed` →
`ubus sys_event update_fail`. **Critically: this check lives in `slpupgrade` only — not in the
bootloader, not in the kernel** (§4: no verified boot), which is why direct MTD writes bypass it.

### The verdict and the real routes

| Route                                                          | Stock fw running?      | Over WiFi?                       | Signature check                       | Notes                                                                                                                                                                           |
| -------------------------------------------------------------- | ---------------------- | -------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| OTA / `/admin/system/image_upgrade` / SD `factory_up_boot.bin` | ✅                     | ✅ / ✅ / SD card                | **❌ blocks us**                      | Only useful _with_ a TP-Link-signed image (downgrades, region/build cross-flash).                                                                                               |
| Memory bug in `slpupgrade`/`/admin` upload path                | ✅                     | would be ✅                      | bypassed by exploit                   | `recv_mime_file`/`check_md5_header`/`parse_conf_first_line`/`ext_fw type:0x%x`/`checkFirmwareMd5Conflict` parse untrusted input; fuzzable. Nothing published for C110 v2 (§10). |
| Root shell → direct MTD write                                  | ✅ (root needed first) | pull image over WiFi, then write | **N/A (no check below `slpupgrade`)** | §7 for root; recipe below.                                                                                                                                                      |
| One-time OpenIPC install (§8)                                  | replaced once          | then forever                     | **N/A**                               | OpenIPC upgrades = `fw upgrade <url>`, unsigned, WiFi.                                                                                                                          |

**Bottom line:** with unmodified stock firmware, you cannot get your _own_ firmware in over WiFi —
the only network-reachable installer is `slpupgrade`, and it pins TP-Link's key. Your options:
(a) exploit the installer (clean but unpublished for this model), (b) get root by other means and
write MTD directly (no signature involved), or (c) one-time OpenIPC flash (§8), after which
firmware upgrades over WiFi work forever without signatures. And if the goal was only app-free
_WiFi settings_ — no flash needed at all, §9A.

### MTD-write recipe (once you have a stock root shell — signature-free)

```sh
cat /proc/mtd                                   # rootfs=mtd6, rootfs_data=mtd7, …
cp $(find_mtd_part config) /sdcard/config.bak   # ALWAYS back up config + art off-device first
# repack a modified rootfs (mksquashfs -comp xz -b 131072, keep <=0x257E00), then:
flashcp -v my-rootfs.bin $(find_mtd_part rootfs) && reboot
```

Writing the partition you are booted from is risky (the overlay complicates it); for full custom
firmware, flash from U-Boot instead (§8.3). And note the SD lever's flip side: if you ever want a
_stock_ build (any region/version from the public S3 bucket, §10), `factory_up_boot.bin` + power
= signed cross-flash with no app and no network.

## 10. Vulnerabilities, CVEs, and myth-busting

**Real, model-relevant:**

- **CVE‑2026‑6250** — _the_ C110 v2 CVE: authenticated format string in the ONVIF service, fixed
  in `1.5.4 Build 260428 Rel.64344n`, leads to forced factory reset. Advisory:
  https://www.tp-link.com/us/support/faq/5128/ ✅
- Family-wide recurring bugs that have hit Tapo/C-series firmware:
  `dsd` `check_user_info` stack overflow (C100, root RCE with admin token —
  https://pwner.gg/blog/2024-01-05-tp-link-tapo-c100), CVE‑2021‑4045 `setLanguage` command
  injection (old C200), CVE‑2023‑27126 shared AES key/IV leaking WiFi creds, CVE‑2025‑8065 ONVIF
  pre-auth overflow (C200 v3/C520WS), CVE‑2025‑14300 pre-auth `connectAp` AP-hijack (C200/C100/
  C425), plus TP‑Link's own stance that UART root is a bug (CVE‑2025‑10991, D230S1).
  Index: https://www.tp-link.com/us/press/security-advisory/ ⚠️
- Shared-key firmware-package encryption (see §6): decryptable by anyone
  (https://github.com/watchfulip/tp-link-decrypt), and TP‑Link's whole S3 bucket
  `s3://download.tplinkcloud.com/` is public: `aws s3 ls s3://download.tplinkcloud.com/ --no-sign-request --recursive` ✅

**Myth — do not chase:** `CVE-2022-37148` **does not exist** (NVD returns zero results — verified
via API ✅) and `CVE-2022-37150` is an unrelated stored XSS in some lab-management PHP app ✅.
The oft-quoted "heap overflow in UDP 40420 handled by `kl_app`" story attached to those IDs is an
AI-echo hallucination; no Tapo daemon named `kl_app` appears in any real dump (ours included —
daemons are `tp_manage`, `dsd`, `cloud-*`, `uhttpd`, `wlan-manager`, `slpupgrade`…). ✅

## 11. Dump hygiene (read before trusting the backup)

The clip dump is our stock-restore insurance, so treat it carefully:

- Re-read the chip at least twice and compare SHA‑256 (`flashrom -r a.bin`, `-r b.bin`).
  A clip-only read can pick up bit errors (VCC droop, bad contact). One mismatch → re-dump.
- Sanity: this dump's `verify` block, RedBoot table, both squashfs superblocks, uImage CRC
  (`Verifying Checksum ... OK` in your boot log) and both rootfs extractions are all clean, so
  the read looks good. ✅
- Keep `c110-1.bin` off-machine (encrypted backup) — flash chips die eventually; the dump is the
  real camera.
