# The intercom on services1 — moving `mercury` off Proxmox without a phone technician (2026-11-16)

**Deployed 2026-11-16.** The hackspace intercom is now `machines/services1/services/pbx.nix`:
bare `services.asterisk` (Asterisk 22.12) on services1, answering **10.3.1.166**, which used
to be a Proxmox VM (`mercury`, VM 128, Sangoma FreePBX 15 / Asterisk 18.26 on CentOS 7). The
VM is stopped with HA's desired state `stopped` and is **not deleted**; the rollback is
`ha-manager set vm:128 --state started`.

Read this before touching the dial plan, and read the module header with it — the header is
where the *rules* live ("one object type per file", "logging is syslog on purpose") and this
file is where the *receipts* live.

## Why this is not a lift-and-shift

The user's framing was "move it to a declarative VM". It became "delete the VM layer",
because everything measurable about `mercury` said the declarative part was not the OS.

| What was on the VM | Measured 2026-11-16 |
| --- | --- |
| Trunks / trunk dial patterns / outbound routes | **0 / 0 / 0** — no provider, no DID, no analog card. It could never place or receive an external call. |
| Registered devices | **2**: a Snom 710 (`1` Frontspace, 10.3.14.180) and a Snom 715 (`2` Workshop, 10.3.14.215), both on VLAN 227 |
| Extensions | 5: `1`, `2`, `3` test, `123` Raccoon, `1337` phyu — the other three had AORs and nothing registered |
| Call history (`asteriskcdrdb.cdr`) | **305 calls, 2024-06-07 → 2026-10-31**, ~12/month. Top rows `1→s` ×92, `1→123` ×68, `1→4225` ×44. |
| Voicemail / recordings | spool **0 bytes** each; `voicemail.conf` had no mailboxes |
| Remote / cloud clients | `zulu_*`, `sangomaconnect_*`, `userman` all effectively empty (5 autogenerated accounts, no emails) |
| Phone provisioning | `/tftpboot` empty, no listener on :69, entire `httpd` access log = one curl of mine → **the handsets were configured by hand** |
| Feature codes | no `*` destination appears in 2.4 years of CDR |
| FreePBX weight | 116 enabled PHP modules, MariaDB 5.5, httpd, node/pm2, on CentOS 7 (EOL 2024-06-30), admin UI reachable from two VLANs |

So the payload is **five endpoints, eight soundboard numbers, eight WAV files (2.2 MB), and a
dial plan of about sixty lines** — which is what `pbx.nix` now is. 104.145… and the rest of it
went away with the VM.

The `72736` "Scream" code was **already dead** and is not reproduced: its ring group points at
group `75736`, which is in no table, and there is no `scream.wav` anywhere on the disk.

## The two decisions that made this zero-touch for the phones

1. **Keep the address.** The handsets have `10.3.1.166` typed into their SIP account, and
   re-typing them means standing at two desks with a phone password nobody in the tree has.
   So services1 answers `.166` as a **second address on `vlan225`**, exactly the shape the
   IdP's `.36` uses (`machines/services1/networking.nix`).
2. **Keep the SIP passwords.** mercury's `/etc/asterisk/pjsip.auth.conf` was copied out
   verbatim into `secrets/pbx.yaml` rather than regenerated. So the phones re-registered by
   themselves; nobody touched a handset. (Extracted with output redirected to a 0600 file and
   spliced into sops by an `EDITOR` script that reads it **by path** — no credential appears
   in `argv`, in the transcript, or in the store.)

`.166` is inside VLAN 225's dynamic range (`.150`–`.253`), so `machines/gw/dns.nix` now emits
`dhcp-host=10.3.1.166,ignore` — without it dnsmasq can hand the phone system's address to a
laptop, and the failure is two silent handsets, not an error. That line is the only
non-table-projection line in the generated `network.conf`, says so in its own comment, and
goes away when the address moves (open in `docs/follow-ups.md`).

## Secrets: the blast-radius finding, which is the part worth remembering

The first version put `pbx_pjsip_auth` in `secrets/secrets.yaml`, and `just check` then died
with

```
error: path '…-sops-secret-pg_pass.drv' is not valid
error: path '…-sops-secret-strata_api_key.drv' is not valid     # on gw's config
```

That is not a bug and not my code: every name in `secrets.yaml` is its own `runCommand`
decrypting the whole file (common/sops.nix), so **all of them are keyed on that file** —
adding one key re-hashes every build-time secret, which is precisely the AGENTS sentence
"change `slack_url` and every unit that embeds any secret is dirtied and restarted". For a
phone password the bill was Grafana, Outline, Affine, nginx-sso, both Strata engines and the
status dashboards, on every box, at once.

The fix is `sops.secrets.<name>.sopsFile`: a **runtime-only secret gets its own encrypted
file** (`secrets/pbx.yaml`, same recipients — verified with the box's own runtime key, exit
status only:

```bash
sudo env SOPS_AGE_KEY_FILE=/var/lib/sops-nix/key.txt sops -d secrets/pbx.yaml >/dev/null; echo rc=$?
```

), `secrets.yaml` reverts to byte-identical, and the deploy dirties nothing that is not the
PBX. `.gitignore` gained two negations, because `**/secrets/*` had `secrets.yaml` tracked only
by the accident of a long-ago `git add -f`.

**Rule worth keeping: before adding a name to `secrets/secrets.yaml`, check whether anything
actually needs it at *build* time. Runtime-only belongs in its own `sopsFile`.**

## Deploy receipts

Order matters, and the reason is ARP: switching services1 while mercury still holds `.166`
gives the network two answers to one address.

```bash
just check                       # evals + fmt, after the secrets.yaml revert
nix build .#nixosConfigurations.services1.…toplevel .#nixosConfigurations.gw.…toplevel
# read the RENDERED files out of the build (rule 10) before touching a live box:
$T/etc/asterisk/pjsip.conf                       # include chain, no external_*_address line
$T/etc/asterisk/pjsip.endpoint.conf              # 5 endpoints
grep -c type=aor $T/etc/asterisk/pjsip.aor.conf  # 5

# 1. the router first: stop the pool handing out the phone system's address
just deploy gw
sudo grep -n "dhcp-host=10.3.1.166" /etc/dnsmasq.d/network.conf
#   ^ this step was run LAST, not first, and the first time it ran it changed nothing:
#     `just deploy` builds from the target's checkout, so an uncommitted change never
#     travels, and the deploy exited 0 on a router that did not have the line. Both halves
#     of that are receipts below — the ARP consequence of switching services1 while the VM
#     still held the address, and the grep on the rendered file that is the only real check.
# 2. the VM down (desired state `stopped`, like VM 108)
ssh -i ~/.ssh/agent-hop-key root@10.3.1.11 'ha-manager set vm:128 --state stopped'
# 3. this box claims the address and starts Asterisk — GOLDEN RULE in one invocation
just switch && readlink -f /run/current-system /nix/var/nix/profiles/system-good
# 4. prove it the way a person uses it
just pbx-status
just pbx-test phone=2 sound=w95              # the Workshop handset physically rings
```

What was checked afterwards. **The first version of this list was written before the switch
and was wrong in two places** — it described the configuration I intended to deploy, not the
system that ran, which is precisely the failure mode `docs/nix-dev-workflow.md` warns about
("a doc's 'measured on the box' may be quoting your own earlier command"). What follows is
what the commands said:

- `pjsip show contacts` → `1/sip:1@10.3.14.180:32768` and `2/sip:2@10.3.14.215:49545`, the
  Frontspace Snom 710 and the Workshop Snom 715, both re-registering by themselves.
- `pjsip show endpoints` / `aors` / `auths` → 5 each, so the one-object-type-per-file shape is
  right (`[1] type=endpoint` and `[1] type=aor` **must not share a file**: `ast_config` merges
  same-named categories, and the result is a PBX that answers nothing).
- `dialplan show from-phone` → 5 extensions + the 8 soundboard codes, all from
  `/etc/asterisk/extensions.conf`.
- `custom/*.wav` → all eight are `PCM, 1 channel, 8000 Hz, 16-bit`, i.e. already in the shape
  Asterisk plays. (Two hand-rolled RIFF parses in this session said otherwise and were both
  wrong: the `fmt ` chunk's data starts 8 bytes after its id, so `channels` is at `+10` and
  `bits` at `+34`. The files were never the problem.)
- `ss -lunp | grep ':5060'` → one UDP socket, and **no TCP listener of any kind**: no AMI
  :5038, no ARI/HTTP :8088, because `manager.conf` and `http.conf` are deliberately absent.
  :5060/udp is the entire attack surface.
- `grep -c "invalid ACL"` on the journal → 0. See the ACL finding below; this one line is the
  check that should have been run first and was run last.

## The four things the deploy actually taught

None of these were visible from the config, and all four cost real time, so they are written
at length. The `mercury` box was already off the network at this point: every minute of this
was a minute the intercom was down, with the old option (start VM 128) always one command
away.

**1. An unresolvable `acl=` on an endpoint fails closed, and the log says so under a word
nobody greps for.** `acl=lan` naming an ACL that does not exist makes every REGISTER answer
`401` and then `Failed to authenticate` — while `pjsip show endpoints/aors/auths` all look
perfect and the migrated passwords are provably byte-identical to the old database. That
misdirected an hour into suspecting the credentials. The line, present the whole time:

```
WARNING acl.c:772 in ast_apply_acl_internal: SIP ACL: Rejecting '10.3.14.215'
        due to use of an invalid ACL 'lan'.
```

All three spellings failed: inline `acl=10.3.0.0/16` and `acl=10.3.0.0/255.255.0.0` are looked
up **as names** (`named_acl.c: ACL '10.3.0.0/16' does not exist … will automatically fail if
applied`), and the named form the shipped `acl.conf` sample prescribes (`[lan]` with
`deny=`/`permit=`; `type=` is invalid there — `Could not find option suitable for category
'lan' named 'type'`) parsed cleanly and still gave `acl show lan` → `Could not find ACL named
'lan'`. So the endpoints carry no ACL, with the reasoning and the compensating controls in the
module's endpoint stanza, and `acl show lan` answering with something is the precondition of
putting it back.

The A/B that proves it, and the instrument worth rebuilding: a **scripted `REGISTER`** sent
from a LAN address answers the whole question in two packets and four seconds, while
"phone someone and ask if it works" costs a trip to the room. It is ~50 lines of Python
socket code, deliberately not committed (rule 1 — this is a diagnostic written mid-incident,
not a tool the fleet should own), and only three things about it matter:

- **bind to a real LAN address**, because the server's ACL is applied to the source; a probe
  that leaks out of `127.0.0.2` proves nothing except that the ACL works;
- **answer the `401` with a fresh `Via` branch** (same Call-ID/CSeq is a retransmission — see
  trap 4 below);
- read the reply: `401` on the first, then `200 OK` = transport + endpoint + ACL + credentials
  all fine; `401` on the second = auth or ACL; no reply at all = dropped before the parser.

With that probe: `acl=lan` present → `401` forever; removed and restarted → `401 → 200 OK`, and
both handsets register within their next expiry cycle.

**2. `confFiles` changes do not restart the daemon, so `just switch` can report success and
apply nothing.** The nixpkgs module ships `restartIfChanged = false`; forcing it to `true` is
necessary but **not sufficient**, because `confFiles` reaches the daemon through
`environment.etc` symlinks, which are not a unit dependency — a dial-plan edit changes no part
of the unit, so systemd restarts nothing. The symptom is the worst kind: config on disk
right, `pjsip show …` answering from the old config, and the deploy log clean. It also made me
conclude, wrongly, that the ACL was not the cause — the process I probed was stale. Fixed with
a `restartTriggers` keyed to a hash of the rendered config text (eval-safe: strings already in
the module, no derivation read, and it cannot hash the SIP secret, which is runtime-only — so
rotating a phone password still does not restart anyone's call). Verified: the switch
following that edit restarted the unit by itself, and both handsets re-registered.

**3. Taking over an address means taking over its ARP entry.** For ~10 minutes the phones were
sending correct REGISTERs into a dead NIC: the router still mapped `.166` to the VM's
`ca:54:07:89:62:0d`. `ip neigh show 10.3.1.166` on `gw` is the two-second answer, and
`ip neigh del` + a ping forces the re-resolution to services1's `c8:d3:ff:a5:b2:25`. This is
not PBX-specific: it applies to **any** address moved from one box to another, which is the
same territory as authentik's `.36`, and belongs in the address-change notes.

**4. Two measurements lied, both because of my own instrumentation.** `ss -lntup` without `-n`
renders 5060 as `sip`, so `grep 5060` "proved" nothing was listening when the socket was
there all along. And the first probe re-sent the authenticated `REGISTER` with the **same
`Via` branch and CSeq**, which pjproject treats as a retransmission of the unauthenticated one
— it replays the cached `401` and never looks at the `Authorization` header, which is enough
to make a perfectly configured server look broken. RFC 3261 wants a fresh branch on a
re-transaction. Also: `pjsip set logger on` prints to the console, not the journal, and running
a second daemon with `-vvvcc` to watch it is not worth it — with `-F` on the managed unit the
journal is the console, and stopping the real service to watch a debug copy takes the phones
down again.

One more, mundane and load-bearing: `pkill -f "asterisk -vvvcc"` matched the shell that ran it,
which is how the service ended up stopped with nothing else running. `pgrep` first, then the
unit.

## Two bugs fixed on the way, and the one left open

- **`external_media_address` / `external_signaling_address = 104.145.12.182`** on mercury — a
  public **Microsoft Azure** address that has never been ours, in the pjsip transport, which
  therefore appeared in every `Contact:` header: both handsets were being told to send
  in-dialog SIP to a stranger's server. There is no trunk, so there is no external address to
  advertise; the new config has none, and `acl.conf` is what decides who may reach :5060.
- **`freepbx.log` was 3.67 GB on a 26 GB root**, 83 % of a sampled tail one deprecation line
  written by `fwconsole job --run` every minute, with no logrotate entry. Here `logger.conf`
  is the module default (`syslog.local0` → journald), and the header says do not add a `full`
  logfile without a rotation in the same commit.
- **Still open, not touched here: the Proxmox boot race.** `mercury` was down for ten days
  before this work because every HA start attempt failed with `storage 'nas2-nfs' is not
  online` — the runbook's own failure, third occurrence (2026-09-30, 2026-10-07, 2026-11-06),
  `max_restart 3` exhausted, service parked in `error`. Root cause is `pve-ha-lrm` starting
  guests before the NAS export is mounted. Moving the intercom off Proxmox removes *this*
  victim; it does not fix the race for whatever else is on that host.

## How root on the VM was obtained, because there were no credentials

Nobody had the root password, so the disk was imaged and a key injected:
`qemu-img convert` a copy (verified with `qemu-img check`), rehearse the injection against the
copy (`SELINUX=disabled`, `PermitRootLogin` default `yes` → an appended
`/root/.ssh/authorized_keys` line, no relabel, no `rd.break`), then do it to the live disk with
the VM stopped, preserving the existing `Phyu@moogle.com` key and leaving
`authorized_keys.bak-20261116` behind. The private half is
`~/.ssh/freepbx-migration-20261116` on services1 and **must be removed from the guest when this
work closes** (`docs/follow-ups.md`). Copies: `services1:/srv/freepbx-mercury/` (borg-backed,
sha256-verified 9.36 GB image + a `mysqldump` of `asterisk`/`asteriskcdrdb` + `/etc/asterisk`),
and two images still on monster1 at `/var/lib/vz/offline-images/`.

## Things not to re-derive

- `services.asterisk.confFiles` is `attrsOf str` — `confFiles."acl.conf" = ''…''`, **not**
  `….text` (the module wraps each value itself; `.text` is an eval error).
- `lib.mapAttrsToList` supplies two arguments: the AOR builder is `ext: _name: …`.
- The nixpkgs module seeds `/var/lib/asterisk` with `cp -r <pkg>/var/lib/asterisk/*` **only if
  the directory does not exist**. `pbx.nix` therefore runs its own `preStart` with `mkBefore`
  and creates the tree, so the sounds and the rendered auth file are re-established on every
  start instead of being a first-boot snapshot.
- Secrets land at boot from the **initrd** (`initrd-nixos-activation-start` imports the SSH
  host keys as age identities), ~3 s before ordinary services — so `preStart`'s hard failure
  on a missing secret is safe, and that failure is deliberate: a PBX that cannot authenticate
  its two handsets should not start quietly.
- **`just fmt` runs `nix fmt -- $(git ls-files '*.nix')`, so it does not see a file you have
  not `git add`ed yet** — and an untracked file is invisible to the flake too (AGENTS rule 5).
  Add first, then format.
- `ha-manager status <uid>` is not valid syntax; the `400 too many arguments` that follows
  `ha-manager set vm:128 --state disabled` comes from `status`, not from `set`.
- `pkill -f "nix build --no-link"` kills the tool call that typed it: the pattern is in that
  shell's own command line.
