# netd: replacing dnsmasq with the twenty-three directives this network uses

**Status, 2026-11-26: built, tested, packaged, and not deployed.**
`services.netd.enable` is `false` on `gw`; `services.dnsmasq` still owns ports 53
and 67. The cutover is one commit (below) and this document is the runbook for it.

- daemon: `crates/netd` (zero external crates; `common-json` + `common-web`)
- NixOS module: `common/netd/module.nix` (`services.netd`)
- renderer: `common/netd/mk-config.nix` — tables in, one JSON document out
- gw's config: `machines/gw/netd-config.nix`, wired by `machines/gw/netd.nix`
- guards: `machines/gw/lib/check-netd-config.nix` (pure eval, runs on the router),
  `netd check` at build time, and the unit's own `ExecStartPre`
- recipes: `just netd-render`, `just netd-check`, `just netd-explain`,
  `just netd-probe`, `just netd-status`, `just netd-leases`

---

## 1. Why, in four measured faults

Every one of these cost a day or more, and none of them is a policy mistake — they
are all properties of dnsmasq's *shape*.

1. **A `dhcp-host` line naming one address twice made dnsmasq exit.** One
   `duplicate dhcp-host IP address 10.3.1.16 at line 30 of
   /etc/dnsmasq.d/network.conf … FAILED to start up` (2026-10-21), and the
   never-give-up policy turned it into a restart loop on the box that answers DNS
   and DHCP for the building. The fix at the time was to emit one line per record
   with every identifier on it (`machines/gw/lib/network-tables.nix` documents
   it). Here it is not expressible: identifiers are a list, addresses are values,
   and two reservations for one address is a *finding* with a sentence.
2. **The generated records file answered the bare name and not the FQDN**
   (2026-10-17). `local=/int.leighhack.org/` makes the box authoritative for a
   zone; it does not complete a hosts entry. Every vhost, every gatus endpoint and
   every Prometheus target asks for the FQDN, so the shadow box was
   self-consistent and useless. Here a name is *either* in the zone *or* a bare
   label, checked at parse time, and both forms are generated from one record.
3. **dnsmasq's unsolicited RA timer dies on a link flap.** Measured three times:
   2026-10-21 (the cutover's re-cabling), 2026-11-19 14:17 (found on 2026-11-21:
   two days of no off-link IPv6 on services1 *and* services2), and 2026-11-26
   11:08–11:13. Nothing fails: no unit, no log line, no dashboard. Clients keep
   their addresses (valid lifetime a day) and lose only the *default route*
   (router lifetime 1200 s), and every `*.int` name is answered on-link, so it
   hides until someone pings something outside the /64. `machines/gw/ra-watch.nix`
   exists to count advertisements on the wire and restart dnsmasq; in netd the
   timer is `now - last_sent >= interval` in a loop that nothing can cancel
   (`crates/netd/src/ra.rs`), so the fault has no state to lose.
4. **The lease file is a channel between two processes, and a channel that can die
   while still answering.** `dnsmasq.leases` is written in place on a descriptor
   dnsmasq opened at startup, so anything that *replaces* the path (`install`,
   `mv`, an editor's save-replace) leaves the daemon writing an orphan. Measured:
   from 2026-10-28 20:51 to 2026-10-31 14:28 the dashboard served 56 rows, every
   one already lapsed, while dnsmasq's live database held 92 leases
   (`machines/gw/lease-reader.nix`). Three modules and a gatus row now exist to
   watch that channel. In netd the lease table **is** the process's memory and the
   dashboard asks `GET /v1/leases`; the snapshot file is written by the same
   process with `tmp` + `rename` and read by nobody else.

The shape that makes all four impossible, rather than fixed:

- one JSON document, generated by Nix, validated strictly (unknown key = build
  failure) — no line-oriented dialect to get wrong;
- one process owns the leases, and the API is a value not a file;
- timers are comparisons in a loop, not timer objects inside a daemon.

## 2. What it implements, and what it refuses to

The specification was the rendered configuration, not dnsmasq's manual:
`/etc/dnsmasq.conf` + `/etc/dnsmasq.d/network.conf` on `gw`, read on 2026-11-27.
Twenty-three directives, four jobs.

**Resolver (`crates/netd/src/dns/`, `dns_server.rs`)**

| dnsmasq | netd |
| --- | --- |
| `domain=`, `local=/…/`, two `addn-hosts`, `dhcp-fqdn` | `dns/zone.rs`: the config's records **and the live lease table**; authoritative, NXDOMAIN inside the zone |
| `server=9.9.9.9` … ×4, `strict-order` | `dns.forwarders`, tried in order, first answer wins |
| `server=/ts.leighhack.org/100.100.100.100` | `dns.conditional` (longest suffix match) |
| `stop-dns-rebind`, `rebind-domain-ok`, `rebind-localhost-ok` | `dns.stop_rebind` + `rebind_ok` + `rebind_localhost_ok` (checked on forwarded answers, parsed) |
| `domain-needed` | `dns.domain_needed` (a single-label name is never forwarded) |
| `cache-size=10000`, `local-ttl=1` | `dns.cache_size`, `dns.ttl` (A/AAAA only — see §7) |
| `dns-forward-max=5000` | `dns.forward_max`, as a **concurrency cap that refuses** rather than a queue |
| `interface=…` ×6 | `dns.listen` + a **source** ACL (`dns.acl`): loopback, every VLAN block, the tailnet. Stronger than an interface filter — a spoofed private source on the WAN is refused |
| TCP for truncation | yes, on the same addresses |
| EDNS(0) | read (client UDP size, DO bit) and advertised (1232) |

**DHCPv4 (`crates/netd/src/dhcp/`, `dhcp_server.rs`)**

| dnsmasq | netd |
| --- | --- |
| `dhcp-range=tag:vlanX,from,to,mask,86400` | `dhcp.pools` (`from`/`to`/`netmask`/`server_ip`/`ttl`), one per VLAN with a range |
| `dhcp-host=<macs>,id:<cid>,set:tag,addr,[v6],name` | `dhcp.reservations` — identifiers are lists; `address` is one value |
| `dhcp-option=tag:…,option:dns-server,…`, `dhcp-option=tag:…,43,01:04:…` | `dhcp.options` (tagged, typed by code; the UniFi blob is generated in `mk-config.nix`) |
| `dhcp-host=10.3.1.166,ignore` | `dhcp.ignored_addresses` |
| `dhcp-name-match`/`dhcp-ignore-names` (`wpad`) | `dhcp.ignored_names` |
| `dhcp-match=set:…,93,7` + `dhcp-boot=tag:vlan227,tag:…,file,server,server` | `dhcp.netboot` (option 93 list, option 77 substring, `when_tags`, bootfile, next-server) |
| `dhcp-authoritative`, `dhcp-fqdn` | always on: NAK for a wrong/stale address, and lease hostnames answer in the zone |
| `option6:23,[::]` | nothing: no DHCPv6 socket is opened, ever (§6) |
| one socket + `IP_PKTINFO` | **one socket per device** with `SO_BINDTODEVICE`, so the VLAN is the socket the request arrived on |
| a missing device with `bind-interfaces` = fatal | a missing device is a journal line; the loop attaches when it appears (this is the restart-loop lesson, `machines/gw/dns.nix`) |

**Router advertisements (`crates/netd/src/ra.rs`)** — one advertisement per VLAN
with an `ra` range, carrying that range's /64s; router lifetime 1200 s, valid and
preferred lifetime 86400 s (dnsmasq's `ra-only` range took both from the lease
time, so clients have always had a day); M = O = 0 (no DHCPv6); solicited
advertisements answered from the raw socket, with the timer as the guarantee
either way.

**API (`crates/netd/src/api.rs`)**

```
GET /v1/leases   {version, now, total, expired, lease_ttl, state_saved_at, state_error, leases:[…]}
GET /v1/status   {version, now, started, uptime, zone, dhcp_interfaces,
                  dhcp_attached, dhcp_missing, dns_listen, dns_cache_entries,
                  leases, api, counters{}}
GET /metrics     Prometheus text (netd_dns_*_total, netd_dhcp_*_total, netd_ra_*_total, uptime)
GET /healthz     ok
```

A lease row: `ip, name, mac, client_id, interface, tag, issued, expires, left,
reserved`. Version 1, additive changes only — `network-status` is a second program
in this repo and the version is how a shape change becomes visible to it.

## 3. The Nix side: one document, no friction

`common/netd/mk-config.nix` is a pure function of the tables; it is builtins-only
on purpose, so `just netd-render` can evaluate it with `nix eval -f` and no
nixpkgs, on the router, in about a second:

```bash
just netd-render | head -c 400        # the document the daemon would read
just netd-check                       # cargo test + `netd check` over that document
just netd-explain mac=c8:d3:ff:a5:b2:25
```

`netd-explain` is the operator's tool and the reason the decision code is a pure
function: it runs the real decision over the real config and the real persisted
lease table and prints the answer, the reason, and every option in the reply.
Measured on 2026-11-27, `just netd-explain mac=c8:d3:ff:a5:b2:25`:

```
answer   OFFER
address  10.3.1.20
lease    86400s
tags     vlan225
why      fixed reservation `services1` holds 10.3.1.20
options in the reply
message-type (53)     OFFER          router (3)            10.3.1.1
server-id (54)        10.3.1.1       domain-name (15)      int.leighhack.org
lease-time (51)       86400          dns-server (6)        10.3.1.1
subnet-mask (1)       255.255.255.0  vendor-specific (43)  01:04:0a:03:01:14
broadcast (28)        10.3.1.255
```

That vendor blob is byte-identical to the live dnsmasq conf's
`dhcp-option=tag:vlan225,43,01:04:0A:03:01:14`.

Two strictness rules do the work of the removed dialect:

- **unknown keys are errors.** A generator that writes `forwarder` for
  `forwarders` fails the build with the path, instead of producing a router that
  forwards to nobody.
- **findings are collected, not short-circuited.** Three mistakes are three
  sentences in one build failure.

`services.netd.config` is validated by `netd check` in a `runCommand`, so the file
under `/etc/netd/config.json` is the *output* of a successful check. The unit also
runs `netd check` as `ExecStartPre`, for the case where someone edited the file by
hand.

## 4. Receipts

**Unit tests.** 82, `cargo test -p netd`, zero warnings under `cargo clippy
--all-targets`. They cover: config parse + every finding (a reservation inside the
pool, a duplicated MAC, a tag that matches nothing, a non-/64 RA prefix, an empty
ACL); DHCP wire format round-trips incl. option overload and a truncated option; the
decision (reservation beats pool, own lease beats requested IP, somebody else's
address is NAK'd, another server's offer is *silence*, DECLINE quarantines, the
pool exhausts honestly, the netboot menu's last-match-wins, `wpad` ignored, a relay
ignored); the DNS parser's defences (compression loop, a 64-byte label, truncation,
EDNS); the zone (A/AAAA/ANY, NXDOMAIN with SOA, NODATA, live leases answering and
lapsing, PTR for an address, the apex's SOA/NS); the RA packet layout; and the lease
snapshot's atomic write.

**The tables round-trip.** `machines/gw/netd-config.nix` rendered against the real
tables: 4 pools, 50 reservations, 188 names, 3 RA interfaces, 6 option rules, 3
boot variants. `netd check` accepts it; `machines/gw/lib/check-netd-config.nix`
returns `ok`.

**The dnsmasq renderer did not change.** `tables.netbootVariants` was restructured
from five rows to three (one row per variant, with the value list the three
`dhcp-match` lines were spelling out). The gate was the rendered text:
`TABLES.netbootLines "10.3.1.32"` before and after is byte-identical, and that
string is the whole content of the generated `network.conf` block.

**Side by side with the live dnsmasq.** netd was run on `services1` against gw's
*real* rendered config with `--no-dhcp --no-ra` and its listeners moved to
`127.0.0.1:5354` (the only changes), then the same questions were asked of
`10.3.1.1:53` (dnsmasq) and of netd with the same client (`netd query`, which
exists so the comparison is one program):

| question | dnsmasq | netd |
| --- | --- | --- |
| `services1.int.leighhack.org A` | `10.3.1.20` | `10.3.1.20` |
| `grafana.int.leighhack.org A` | `10.3.1.1` | `10.3.1.1` |
| `aibox.int.leighhack.org AAAA` | `2001:8b0:1d14:225::32`, `fd99:dead:beef:225d::32` | same |
| `mqtt.int.leighhack.org A` | `10.3.1.20` | `10.3.1.20` |
| `nonexistent.int.leighhack.org A` | NXDOMAIN, empty authority | NXDOMAIN, **SOA in authority** |
| `example.com A` | forwarded | forwarded |

The one deliberate difference is the last row's second column: RFC 2308 says a
negative answer carries the zone's SOA so a downstream cache knows how long to
believe it, and dnsmasq answers with no authority section at all. Including it is
strictly more correct and is the only answer that changes shape.

The API was exercised live in the same run: `/healthz`, `/v1/status` (uptime,
attached/missing interfaces, counters), `/v1/leases`, `/metrics`, and 404 on an
unknown path.

**The cutover guards were exercised, not just written** (2026-11-27, on `gw`, by
flipping the two switches in a staged tree and evaluating):

- with `services.netd.enable = true` and dnsmasq still enabled, exactly **one**
  assertion fails and it is the intended one — `services.netd and services.dnsmasq
  cannot both be enabled: two DHCP servers on port 67 and two resolvers on port 53…`;
- with both switched (netd on, dnsmasq off), **zero** assertions fail and
  `/etc/netd/config.json` is defined — pointing at
  `netd-config-checked.json`, i.e. the document the daemon would be handed;
- `nix build --dry-run` of that file's plan is `crates-workspace-deps` → `netd` →
  `netd-config.json` → `netd-config-checked.json`, and nothing else of the fleet,
  and the build itself **succeeded** on services1 (2026-11-27): crane compiled
  `netd` out of the workspace with `sharedCrates = ["json" "web"]`, ran
  `netd check` over the Nix-rendered document inside that build, and the resulting
  `netd-config-checked.json` parses to **exactly** the document
  `just netd-render` prints (`builtins.fromJSON`/`toJSON` on both, `cmp`-equal;
  the store file is pretty-printed, so the bytes differ and the value does not).
  That is the whole Nix↔Rust seam proven end to end without touching a socket.
  (Note for whoever lands this: **adding a workspace member invalidates
  `crates-workspace-deps` for every crate**, because the dependency derivation is
  keyed on the workspace manifest and lock — so the next full build anywhere
  compiles the whole dependency tree once, ~25 min of 4 cores here. That is
  crane's design and `common/crane.nix` says so; it is not specific to netd.)

Not yet exercised live: DHCP over a real device and unsolicited RAs (both need
ports 67/ICMPv6 on a real VLAN, which is the cutover), and `netd probe` against
the live dnsmasq.

## 5. The cutover

One commit:

```nix
# machines/gw/netd.nix
services.netd.enable = true;

# machines/gw/dns.nix
services.dnsmasq.enable = false;

# machines/gw/default.nix — imports
#   drop ./ra-watch.nix      (its fault cannot exist: ra.rs has no timer to lose)
#   drop ./lease-reader.nix  (nothing reads a lease file any more)
```

`common/netd/module.nix` **asserts** that `services.dnsmasq.enable` is false when
netd is enabled, and that `services.resolved` is off, so half a cutover is a build
failure rather than two daemons racing for a socket.

Then, in this order, watching each step:

1. **Before the switch**, on `gw`: `sudo systemctl stop dnsmasq` is *not* needed —
   the switch does it — but take a `dhcp-lease` snapshot first
   (`just netd-leases` will not work yet; `sudo cat
   /var/lib/dnsmasq/dnsmasq.leases` is what to save). Lease persistence across the
   cutover is the one thing netd cannot inherit: it starts with an empty table, so
   every client keeps the address it already has (nothing *tells* it to change) and
   re-REQUESTs it on renewal; netd's allocator hands back what a client asks for
   when it is free (`dhcp/decision.rs`, `choose`), so the address survives. The
   risk is a client that asks for an address inside the pool while another client
   holds it — netd NAKs and the client takes a new one, which is correct and
   visible in the lease table.
2. **Switch and confirm in one invocation** (GOLDEN RULE):
   `just deploy gw` from another box, or `just switch` on `gw` — the latter if you
   are already on the box (rule 27).
3. **DNS first**, because it is what everything notices:
   `dig @10.3.1.1 grafana.int.leighhack.org` (should be 10.3.1.1), `dig @10.3.1.1
   services1.int.leighhack.org`, `dig @10.3.1.1 example.com`, and from a wireless
   client `dig @10.3.2.1 …int.leighhack.org` (the per-VLAN option, permissions
   included).
4. **DHCP**: `just netd-probe interface=vlan226` — a whole lease cycle from the box.
   It binds the client port on that VLAN; the router is not a DHCP client there, so
   the port is free. Then watch `/v1/leases` and check a real device renews.
5. **IPv6**: `sudo systemctl start ra-watch` once, *before* removing the module's
   import, and expect it to pass by counting netd's advertisements — it is a
   dnsmasq-agnostic meter (one `tcpdump` per VLAN), so it is also the acceptance
   test for `ra.rs`. Then drop the import in the next deploy. A client that never
   loses its default route is the other half.
6. **The dashboard**: until `network-status` learns `--leases-url`
   (`docs/follow-ups.md`), `/api/leases` on `network-info` will be a 503 once the
   lease file stops being written — the page is honest about it, and the gatus row
   goes red. That is the intended signal that the last reader of the old channel
   is waiting for its half of the change.

Rollback is the same commit reversed: `services.dnsmasq.enable = true` and netd
off, and dnsmasq re-reads its lease file as it left it.

## 6. What this deliberately does not do

- **No DHCPv6.** The network's IPv6 is advertised, not leased; the old config's
  `option6:23,[::]` said the same thing. A DHCPv6 server would also have to own
  the `dhcp-host=…[v6]` bindings the retired appliance honoured and nothing
  replaced (`common/dns-records.nix`'s `ipv6` field says so).
- **No RDNSS/DNSSL in the RAs.** dnsmasq did not send them, so IPv6-only
  resolution is not configured today and this does not change it. Adding it is a
  behaviour change on every client and belongs to its own change.
- **No TFTP.** `dhcp-boot` names aibox as the server and the client fetches from
  aibox (`machines/aibox/netboot.nix`); netd never reads the file.
- **No relays** (`giaddr != 0` is ignored with a reason), no PXE proxy, no
  `--dhcp-boot` for a device that is not in `dhcp.netboot`, no vendor-class
  piracy, no DNSSEC validation, no DNS-over-TLS.
- **No negative DNS caching.** NXDOMAIN is answered, not cached. dnsmasq cached
  it; a rerun of a miss costs one upstream query, and a negative cache is another
  expiring table to reason about.
- **Not authoritative for the reverse zone.** PTR is answered for any address in
  the tables or in the lease table, and an unknown address in a network we hand out
  gets NOERROR with no records (not NXDOMAIN, which would be a lie). It does not
  answer NXDOMAIN for reverse names outside those networks — that would forward,
  and `in-addr.arpa` for 10/8 would be sent upstream, as dnsmasq did.

## 7. Known limits, written down before they bite

- **The dnsmasq→netd lease table is not inherited.** See §5 step 1. If every
  client is asleep at the cutover the table refills within a day, and nothing
  breaks meanwhile (a client keeps its address, and its renewal is the event that
  records it).
- **The DNS cache stores A/AAAA only**, because every other type can contain a
  compression pointer into a message the cache does not keep; caching those would
  hand the next client a pointer to nothing. A forward of any other type is a
  round trip to the upstream every time. Measured acceptable: `int.` names are
  authoritative and never forwarded, and the upstreams are ~10 ms away.
- **One DHCP thread, one socket per device, a 20 ms poll.** DHCP is a few packets
  per minute; the poll exists so a request arriving on the fourth VLAN is not
  delayed behind three empty reads. It costs one wakeup per 20 ms.
- **The `resolv.conf` on the box still points at `127.0.0.1`** (`machines/gw/dns.nix`
  writes it) — so the box's own resolution goes through netd once it is the
  resolver on `0.0.0.0:53`. That file does not change at the cutover.
- **`netd check` needs a build**, so `just netd-check` refuses on `gw` like every
  other compile-adjacent recipe. The eval-only guard
  (`machines/gw/lib/check-netd-config.nix`) is what runs on the router, via
  `just check-eval`.
